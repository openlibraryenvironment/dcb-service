= Lender checkout and patron blocks
:description: How DCB checks a Polaris lender's copy out to the borrowing library's virtual patron, and when it overrides a patron block.

When a patron borrows an item from another library, DCB checks the lending library's copy out to
the borrowing library's virtual patron in the lender's Polaris. The copy then shows *Checked Out*
at the lender, and the transfer hold is satisfied.

By the time DCB makes this checkout, the item is already with the patron. If Polaris refuses it,
the loan still goes ahead, but the lender's copy stays *Transferred*, and checking it in sends it
round the transfer loop again.

== When DCB overrides a patron block

Polaris can refuse the checkout because of a block on the virtual patron (PAPI error -6101,
"Patron block"). DCB then overrides the block once, through the Application Services check-out
workflow, unless a person placed a block on the virtual patron.

[cols="2,1",options="header"]
|===
| Blocks on the virtual patron | DCB

| None stored, but Polaris refuses at checkout. Polaris works some blocks out at circulation time and never stores them.
| Overrides

| Only an address check or an expired registration. A virtual patron brings these on itself.
| Overrides

| Any other stored block, such as one a member of staff placed
| Does not override. The checkout fails and the request's audit says why.

| The stored blocks cannot be read
| Does not override
|===

Before overriding, DCB reads the patron's circulation blocks from Polaris. Their descriptions are
logged at DEBUG; the INFO log says only how many there were.

== What the library needs

The Polaris account DCB signs in with needs the permission to override patron blocks at checkout.
Without it, Polaris refuses the override and the request's audit records "Virtual checkout failed".

== Setting

[cols="1,1,3",options="header"]
|===
| Setting | Default | Meaning

| `override-blocks-at-checkout`
| `true`
| Set to `false` on a Polaris Host LMS to stop DCB overriding a block at checkout. The checkout is then refused, and the request's audit says so.
|===

== When the lender checkout fails

If the checkout still fails, the loan stands and the request stays *Loaned*. DCB:

* records "Virtual checkout failed" in the request's audit, with the lender's answer, and
* sets the request's `needsAttention` flag.

Staff at the lending library should check the copy out to the virtual patron by hand. Until they
do, the copy shows *Transferred* and is routed again when it is checked in.

To list these requests, query GraphQL with `patronRequests(query: "needsAttention:true")`. The flag
is also set when a checkout in the patron's own library fails, and when a request has been tracked
for too long, so read the audit to see which applies.

DCB does not yet retry a failed lender checkout.

== Renewals at the lender

When the patron's own library renews a loan, DCB renews the lender's copy by checking it out to
the virtual patron again through PAPI. Polaris gives each virtual patron its own barcode, with
the prefix set by `services.patron-barcode-prefix` (default `DCB-`), so DCB asks Polaris for the
virtual patron's barcode by patron id before it renews. Before this, every renewal at a Polaris
lender failed with PAPI error -4005, "Invalid patron barcode".

After upgrading, compare due dates on loans that are already open: copies whose renewal failed
earlier still have the old due date at the lender.
