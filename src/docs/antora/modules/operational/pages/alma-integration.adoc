= Alma integration

How OpenRS DCB talks to Ex Libris Alma, and the constraints that shaped it.

This page is for people extending or operating the adapter. Consortium staff bringing a new
Alma institution into OpenRS want xref:operational:alma-setup.adoc[] instead.

== The shape of the adapter

Two classes carry the integration:

`AlmaHostLmsClient`:: The `HostLmsClient` implementation. Everything DCB's request workflow
asks of an ILS — place a hold, create a virtual patron, check an item out, track a request —
is answered here. No Alma-specific behaviour exists outside this package.

`AlmaApiClient`:: The REST layer. A Micronaut declarative client with `default` methods for
each Alma operation, so path construction and paging live in one place rather than at every
call site.

The separation matters for a practical reason: Alma's API surface is wide and inconsistent,
and the adapter has to absorb that inconsistency so DCB's workflow engine never sees it.

== Authentication

=== The API key

The key goes in a header, never a query parameter:

[source%nowrap,http]
----
Authorization: apikey l7xx0123456789abcdef
----

IMPORTANT: Sending the key as `?apikey=` returns a Tomcat HTML `400` with no useful body.
This looks like a malformed request and is in fact a rejected credential. If you are
debugging an Alma call that fails with unexplained HTML, check this first.

The key needs *Users* and *Bibs* read/write and *Configuration* read-only: the client
writes nothing under `/conf`. User requests sit in the Users area and item requests in Bibs;
Alma has no separate Requests area. A key missing one of these fails only on the operations
that need it, so a partly-permissioned key presents as an intermittent integration rather than
a broken one.

=== Patron authentication

Patron credentials are verified with Alma's documented authentication operation — `op=auth`
against the user record, with the credential in the `Exl-User-Pw` parameter. The adapter
refuses any authentication profile it cannot actually verify rather than returning a
permissive answer, because a verifier that cannot check a credential must fail closed.

CAUTION: No credential, PIN, barcode or token is ever logged, at any level, including inside
constructed exception messages. Alma error payloads can echo the request, so error details
are filtered before they reach a log line.

== Errors

Alma reports failures as a JSON or XML error body carrying one or more `errorCode` values,
usually with HTTP 400. The adapter raises these as a typed `AlmaApiException` exposing the
codes, so callers branch on the code rather than on message text.

This matters because several Alma conditions are indistinguishable by status alone. "User
not found" is the clearest case: it is an ordinary outcome when DCB checks whether a virtual
patron already exists, and an error anywhere else.

[source%nowrap,java]
.Branching on a code, not a message
----
.onErrorResume(AlmaHostLmsClient::isVirtualPatronNotFoundError, error -> Mono.empty())
----

== Paging, and why every list is paged

Alma paginates everything and silently truncates to a default page size. Three defects came
from reading only the first page: a patron's loan not found when renewing, items missing
from availability on a large bib, and holds miscounted.

The rules the adapter follows:

* Every list endpoint is read through a paging helper, never a single call.
* `total_record_count` spans every page, so it is the only trustworthy source for a count.
* Per-bib fan-out is bounded, because one availability check must not become an unbounded
  number of calls to a member system.
* A hold search stops after `MAX_HOLD_PAGES` (500 requests). The bound is stated in the code
  because the types cannot state it.

== Placing holds, and idempotency

=== The problem

If DCB places a hold and loses the response — a timeout, a restart — a retry would place a
second hold. So before creating, the adapter looks for one it has already placed.

=== Why the match is on `comment`

The obvious key would be the item id, and the first implementation used it. That is wrong
twice over.

*The patron id is not always DCB's.* At the supplying agency the local patron id is a DCB
virtual identity, so anything found under it belongs to DCB. At the borrowing agency it is
the patron's *real* Alma account. A hold that patron placed for themselves, on the same
item, sits in the same list — and matching on item id alone adopts it. DCB would then track,
and on finalisation cancel, a request it never placed.

*The item id may not be there.* Alma's documented `user_requests` list payload does not
include `item_id`. It also omits `request_id`, which Alma certainly does return, so the
documentation is describing the input shape rather than the response — meaning the presence
of `item_id` in the list is unverified either way. A match that depends on it is a match that
may silently never fire.

`comment` is documented in the list payload, is an input field on request creation, and
round-trips. So DCB writes its own marker there and matches on that:

[source%nowrap,text]
----
Consortial loan [DCB-REQUEST:0f9c2b7e-5a41-4c8e-9d33-21ab7c0e4f55]
----

The marker is bracketed so that one request id cannot match another it is a prefix of, and
carries the DCB patron request id, so adoption is exact: a hold placed for a *different* DCB
request is not adopted either.

=== Failing closed

When no DCB patron request id is available, the adapter does not search at all — it creates.
A duplicate hold is a visible, correctable fault; adopting a stranger's request is a silent
one that ends in cancelling a patron's own hold.

NOTE: `additional_id` looks like the natural field for a marker and is not usable — Alma
documents it as an output parameter.

== Preventing renewal

When another library places a hold on an item a DCB patron has on loan, DCB asks the
borrowing system to stop that loan being renewed.

=== Why it is done on the item, not the loan

`rest_item_loan.xsd?tags=PUT` marks `user_id`, `item_barcode`, `loan_status`, `loan_date`,
`return_date`, `process_status`, `mms_id`, `holding_id` and `item_id` as output parameters.
`due_date` alone carries "Can be modified using PUT or the renew API", and `POST` to a loan
supports only `op=renew`.

So *there is no writable renewal flag on an Alma loan*. That is less of an obstacle than it
first appears, because no adapter denies renewal on the loan. Sierra sets the item's "No. of
Renewals" fixed field to 255; Polaris posts a blocking note to the item's owning
organisation; Koha stamps a collection code the library lists in `ItemsDeniedRenewal`. Each
changes the *item* so the ILS's own circulation rules refuse the renewal.

Alma's equivalent is the item policy — "the item's override policy for loan rules". DCB
already sets it when creating a virtual item, so it is a field DCB is known to write
successfully against a live tenant rather than one inferred from a schema.

=== What DCB does

. Reads the virtual item by bib, holding and item id.
. Refuses unless the holding carries the `DCB_VIRTUAL_COLLECTION` call number, so denying
  renewal can never be applied to one of the library's own items.
. Sets `item_data.policy` to the configured `no-renew-item-policy`, defaulting to
  `DCB_NO_RENEW`.
. Reads the item back, and fails if the policy did not take.
. If any of that fails, writes a do-not-renew note to the virtual item's `fulfillment_note`,
  which Alma shows during circulation, and *still* raises the original error so the workflow
  audits the request and marks it `UNSUPPORTED`. This mirrors the Polaris client. The note is
  best effort — failing to write it is logged and never masks the original failure.

The guard runs before that fallback, so an item DCB did not create is refused outright rather
than written to with a note instead. An earlier implementation put this note on the library's
*own* item and nothing removed it when the request finished, so notes accumulated on real
holdings. Writing only to the virtual item, which DCB deletes at FINALISED, is what makes the
fallback safe to reinstate.

`PreventRenewalCommand` carries `localBibId` and `localHoldingId` alongside the item id
because Alma addresses an item by all three and offers no lookup by pid alone. The barcode is
deliberately not used: `pickupItemBarcode` is populated only on the pickup-anywhere path.

=== What the library must configure

WARNING: DCB sets the policy but cannot create the rule that acts on it. A Fulfilment Unit
loan rule matching that policy must disallow renewal, or DCB will set it, report success, and
the renewal will still go through. This is the same division of labour as Koha's
`ItemsDeniedRenewal` — the adapter writes a label, the library writes the rule.

The staff-warning fallback does *not* cover this case. Nothing failed, so no note is written:
DCB set the policy exactly as asked and only the rule is missing. The fallback covers a failed
*write* — most often a site that has not created the policy code at all.

The read-back therefore proves the policy was written. It does not prove renewal is now
denied: that rests on deployment state DCB cannot see.

A previous implementation appended a note to the library's own item record. That was removed:
the note was never taken off once the request finished, so it accumulated on real holdings.

== Patron mapping

An Alma user becomes a DCB `Patron` as follows:

[cols="1,2"]
|===
| DCB | Alma

| `localId` | `primary_id`
| `uniqueIds` | `external_id`
| `localBarcodes` | identifiers of type `BARCODE`, falling back to `primary_id`
| `localPatronType` | `user_group` code
| `localHomeLibraryCode` | `campus_code`
| `expiryDate` | `expiry_date`
| `isBlocked` | any user block with status `ACTIVE`
| `isActive` / `isDeleted` | `status`
|===

Two details are easy to get wrong:

*The barcode fallback.* An institution's `primary_id` is often an SIS or IdP identifier
rather than a card number. It stands in as a barcode only for a user who has no barcode
identifier, so that a patron without a card is still actionable.

*An absent status means active.* Only an explicit `INACTIVE` or `DELETED` blocks the patron.
Treating a missing status as inactive would lock out every user of a tenant that does not
populate it.

== Shared Alma tenants

A single Alma tenant can host several participating libraries — a Network Zone, or one
institution whose campuses are separate members of the consortium. Setting `shared-system:
true` on the Host LMS supports this. It disables two things that cannot be correct on a
shared system: `default-agency-code`, and the `Location: *` wildcard.

Agency resolution then depends on each patron resolving to their own library, which is what
`localHomeLibraryCode` is for — and until recently the Alma adapter set it for no one.
Mapping `campus_code` supplies it.

What a shared Alma tenant must therefore do:

. Populate `campus_code` on user records. It is an optional Alma field; where it is empty,
  that patron resolves to no agency.
. Map each campus code to its agency, via Location mappings.
. Leave `default-agency-code` unset — the configuration validator rejects the combination.

WARNING: One gap remains. `virtual-item-library-code` is a single value per tenant, so
virtual items are created at one library even on a shared system, where the borrowing
patron's own library would be preferable. Koha already prefers the patron's home branch;
Alma does not yet.

== Live availability

Alma's `BaseStatus` has two values, `0` and `1`, in place or not. The process type says why
an item is not in place, and `deriveItemStatus` reads both, against Alma's `PROCESSTYPE`
code table:

[cols="2,1"]
|===
| Alma | DCB

| base `1`, no process type | `AVAILABLE`
| `LOAN` | `CHECKED_OUT`
| `REQUESTED` with base `1` | `AVAILABLE`
| every other process type, and base `0` with none | `UNAVAILABLE`
|===

`TRANSIT` is unavailable because Alma uses it for an item going home and one going to fill
another patron's hold alike; `ILL` because the item is lent through Alma's own resource
sharing. A code outside the table is unavailable and named in the item's decision log. The raw
values are kept in `rawDataValues` as `baseStatus` and `processType`.

Due dates are read from the loan, not the holding record. The holding's date is not the
borrower's.

== Harvesting

Records are harvested over OAI-PMH. The endpoint DCB derives is:

[source%nowrap,text]
----
{base-url}/view/oai/{institution-code}/request
----

The institution code here is the OAI institution code, which is not always the same string
as the Alma institution code — it is worth confirming rather than assuming.

Two failures look alike and are not:

* `error_code 21` from OAI means the institution is not authorised for OAI at Ex Libris.
  This is an entitlement problem, not a configuration one, and no amount of local
  configuration will fix it.
* An empty harvest with no error usually means the OAI set is wrong or empty.

If Alma sits behind IP whitelisting, the DCB server's address must be whitelisted for OAI
specifically, not only for the REST API. These are often controlled separately.

== Pass-through from Primo

An Alma site keeping Primo can still send patrons into OpenRS for items it does not hold. The
path is a link on the Alma services page into a pre-filled search in the OpenRS discovery UI, and it needs no
code on either side. The Alma configuration is in xref:operational:alma-setup.adoc#primo[Linking to OpenRS from Primo].

=== Why a search and not a record link

Discovery UI record URLs are `/items/{recordKey}`, and the key is parsed by `RecordKey.parse`,
which *requires* a source segment. Primo has no way to know that key, so a direct record link
is not constructible from an OpenURL. A fielded search on the identifier is the correct
target rather than a compromise.

=== Why the identifier match works

`SearchQueryBuilder` routes `isbn` to a nested query against `metadata.identifiers`, matching
on `value` with a `namespace` term, rather than to the flat `isbn.keyword` field. That was
DCB-1181: the flat field misses the 10- and 13-digit variants the metadata holds. Alma sends
whichever form its record carries, so the flat field would have failed on a large share of
inbound links.

=== The bound

One inbound link is one search. It fans out to nothing, reads only the shared index, and the
search route is anonymous like every other search — no patron identity is involved until a
request is placed.

=== The limit worth knowing

The nested identifier query matches on an analysed `text` field, so an identifier can match
more than one cluster — different editions, or a record where the identifier appears in more
than one namespace. That is correct for a search and is exactly why this path lands on
*results* rather than redirecting to a record. Sending a patron directly to a single guessed
edition would be worse than showing them the matches.

A dedicated resolver endpoint is planned. It will need an exact-match path for the cases
where a single answer is required; the search route is deliberately not that.

== Things to be aware of

* Virtual bib, holding and item records are created at the supplying and borrowing ends and
  are deleted when the transaction finalises. When virtual item creation fails, the holding
  created moments earlier is deleted too — otherwise a failed request leaves an orphan.
* Identifiers are encoded as single path segments. Alma identifiers can contain characters
  that alter a URL's structure if interpolated raw.
* Changing a patron's group preserves the rest of the user record. Alma's user `PUT` replaces
  the record, so a partial payload silently deletes fields.
* Virtual bib titles and authors are escaped, and placeholder catalogue fields are not sent.
  The bib carries no 001 or 005, which Alma writes itself, and a 500 note naming it as DCB's.
  `deleteBib` reads the bib and its holdings first and deletes only while it is suppressed,
  carries the note, and holds nothing but DCB's own holding; otherwise it raises and the
  record stays.
* Before creating a virtual item, the supplier's barcode is looked up in the borrower's
  Alma. An existing item raises `DuplicateItemBarcodeException` before anything is created;
  Alma's `401689` means the barcode is free.
* A supplier hold goes to `sharing-circ-desk-code` as a desk pickup when that is set;
  otherwise to `sharing-library-code`, or to `alternative-sharing-library-code` for an item
  whose owning library is the sharing library. Alma shelves an item scanned in at its hold's
  pickup location rather than sending it, and DCB sees a dispatch only as a transit.
* The adapter states which item states it can act on rather than attempting every state.
